# 2026-08-31

## 修复：录屏产出 3KB 空壳 + 自检误报「音轨静音」

### 现象
用户勾选录屏播放 `动物与道德高度演讲视觉页面_自动播放.html`，产物只有 2.8KB / 2.1KB，
弹窗报「录到了音轨，但里面是静音数据 / 音轨峰值 0.0000 / 送入音轨数 1 / 产物含音轨 是」。

### 定位过程（关键：别信弹窗，直接解 MP4）
用 python 解 moov 得到：
- **只有 1 条 trak，hdlr=`soun`，完全没有任何 `vide` 视频轨**
- `stts entries=0`、`stsz sample_count=0`（0 个样本）
- `mvhd duration = 127ms / 85ms`
- mdat 仅 2048B / 1366B

结论：**不是音频问题，是录制在启动 100 多毫秒时就被停掉了**。
H.264/AAC 编码器初始化要几百毫秒，来不及吐样本 → 视频轨连 trak 都没建，
音频只留 stsd 里写着 mp4a 的骨架。旧自检用正则 `/mp4a|soun/` 判断「含音轨」→ **必然误报**。

### 根因
v3.1 直接全屏录屏：`setFullscreen(true)` → sleep 450ms → `getDisplayMedia`。
Electron 的 `setFullScreen()` 返回时窗口还在做样式重建 + DWM 重新合成（余波数百 ms~1s），
捕获源在余波末尾失效 → video track `ended` → `session.onExternalStop` resolve →
父层立刻 `send({type:'stopPlay'})` → `finishRecording()` → 成片只有 127ms。
（人不可能在 127ms 内手动停共享，所以只可能是自动路径。）

### 改动
1. `electron/main.cjs`：新增 `waitFullscreenSettled()`，`zt:set-fullscreen(true)` 改为
   await 等到 `enter-full-screen` 事件落地 + 250ms 余量才 resolve（2s 超时兜底；
   已是全屏则不再有事件，走 100ms 余量）。
2. `src/App.jsx` `handleStartPlay`：全屏落定后再 sleep 300ms 才建捕获。
3. `src/App.jsx`：`onExternalStop` 加 1.5s 保护窗 —— 起步 1.5s 内轨 ended 视为全屏余波误触发，
   **忽略并继续录制**（否则就是几 KB 空壳 + 把排查方向带偏到音频上）。
4. `src/App.jsx`：自检重写 —— 新增 `probeTracks()` 数 vide/soun 轨 + stsz 样本数；
   新增录制时长、首个数据块、MediaRecorder 错误、送入轨数(视/音)；
   录制 <1.5s 直接判「过短」并改报错文案；`probeAudioLevel` 在 <0.5s 时不再测电平
   （那时"静音"是果不是因）。
5. `src/recorder.js`：`stop()` 返回 `durationMs / recError / firstChunkMs`；
   `onExternalStop` resolve 出「距启动多少 ms」；启动日志补送入轨数。
6. 顺手修：`probeAudioLevel` 的 AudioContext 从未 close → 每次录制泄漏一个，
   内核约 6 个配额，录几次后 AudioContext 建不出来。

### 验证
- 新 `probeTracks()` 在两个真实失败产物上跑出 `{video:0, soun:1, samples:0}`，旧逻辑则是「含音轨=是」。
- `npm run build` 通过；已 `rm -rf dist` 清理堆积（emptyOutDir:false，之前堆到 3 个 js）。

### 待用户验证
需重新打包 exe（dist-electron 里那份是 23:33 的旧代码）或走 `npm run dev:electron` 再录一次。
若新自检显示「录制时长正常但产物含视频轨=否」，则是 H.264 High profile(avc1.640028)
编码器不可用，下一步把 `pickMime()` 首选降到 Baseline(42E01E)。

## 修复（下午）：WebCodecs 高清路径音轨全零 —— 定案「主线程读 PCM 必被饿死」

### 现象
WebCodecs 路径（清晰度达标，32s/65.7MB ≈ 16Mbps）音轨无声音。弹窗：
「音频收包/AAC块 0/0、产物含音轨 是、音轨峰值 0.0000」。

### 定位（解 MP4 是决定性的）
`scripts/mp4probe.py`（本次新增，python 解 box）跑两个产物：
```
05-39-40.mp4 22.0MB  mvhd 11.65s  trak0 avc1 317帧   trak1 mp4a count=0
05-34-31.mp4 65.7MB  mvhd 32.36s  trak0 avc1 943帧   trak1 mp4a count=0
```
音轨 **stsz sample_count 全是 0** —— 不是静音，是一个样本都没收上来。
弹窗「产物含音轨=是」仍是旧正则 `/mp4a|soun/` 的误报（只写了 stsd 骨架也算「有」）。

### 根因（三版本对照，铁证）
同一个 `createMediaElementSource` src 节点，三种消费方式：
| 版本 | 消费方式 | 结果 |
|---|---|---|
| fe38419（rec-screen-freeze-fix） | MediaRecorder 消费 MediaStreamDestination 轨 | 有声 |
| befe498（WebCodecs 初版） | MediaStreamTrackProcessor 读同一轨 | 全零 |
| 本地未提交改动 | ScriptProcessor.onaudioprocess 读同一 src | **0 次回调** |

共性：**凡是要在主线程被调度去读 PCM 的方案，都被录制管线饿死**（rAF 重绘 2520×1680
+ VideoEncoder.encode + muxer 把主线程占满）。MediaRecorder 的采集在浏览器内部线程完成，不受影响。

另有一个放大问题的改动：本地把 `USE_WEBCODECS` 判定从 `=== '1'` 改成了 `!== '0'`，
**语义写反** —— 没设过开关时 `null !== '0'` 为真，默认反而变成「开」，
与注释和 HEAD 提交（b0d27a2 明确要回退 MediaRecorder 保声音）的意图相反。

### 改动（v3.3）
1. **新增 `src/recAudio.js`**：音频采集独立成模块。
   - `ensureGraph()`：WebAudio 图按「元素身份」缓存，`createMediaElementSource` 对同一元素
     只能调一次（第二次抛 InvalidStateError）；元素换了就 close 旧图重建（AudioContext 配额约 6 个）。
     修了旧代码 `__ztRecCtx` 与 `__ztRecSrc` 缓存不同步的隐患。
   - `startAudioCapture()`：**MediaRecorder 采集**（沿用 fe38419 已验证有声的同一条链路），只录音频。
   - `encodeAudioToAac()`：webm/opus → `decodeAudioData` → PCM(planar f32) → AudioEncoder AAC。
   - `getAudioTrack()`：给 MediaRecorder 兜底路径复用同一张图。
2. **`src/recorder.js`**：WebCodecs 只管视频（保 CBR 清晰度），音频交给上面那条路。
   - 视频 chunk 先缓存入数组（音频要录完才编得出来），`stop()` 时按时间戳**交错**封装。
     查过 mp4-muxer 5.2.2 源码：非分片模式下两条轨各自累积，调用顺序不影响正确性。
   - **音频必须与视频同时停**：先 `audioCap.stop()` 发起停止（rec.stop() 同步生效），
     再 await 视频 pump/flush，最后 await 音频解码编码（与视频收尾并行）。
     写反会让音轨比画面长最多 4.5s（尾端拖空白）。
   - 删掉 `getAudioTrack`/`installAudioTap` 两个本地版本（失效方案）。
   - `USE_WEBCODECS` 修正为默认开、`=== '0'` 才关。
3. **`src/App.jsx`**：`probeTracks()` 重写为按 trak 分组，分别统计 vide/soun 的
   **stsz 样本数**；mp4 的「含音轨」判据改为 `soun>0 && audioSamples>0`（彻底消灭误报）。
   自检面板新增：音频链路 / 音频PCM帧·AAC块 / 音频链路错误。
4. **`scripts/mp4probe.py`**：新增，解 moov→trak→hdlr/stsz，一眼看清有几条轨、各写了多少样本。
5. **`测试工程/音频链路自检.html`**：免 F12 的验证页，遍历 5 种 mime 各录 2 秒并尝试解码，
   输出「采集→解码→峰值」矩阵。用途是验证新链路最大的风险点：
   `decodeAudioData` 能否解 MediaRecorder 输出的流式 webm。

### 结论
清晰度和声音**不是**二选一：WebCodecs 管视频（CBR 足额码率）+ MediaRecorder 管音频，
两条都是已验证的部件，最后交错封装。`npm run build` 通过（39 modules）。

### 音频链路自检结果（用户实跑 `测试工程/音频链路自检.html`，2026-08-31 14:08）
环境：Chromium / MediaRecorder 支持 / AudioEncoder 支持 / AudioContext 48kHz running。
采集 2 秒 → 解码 → 测峰值，四个 mime 全通：

| 封装格式 | 结果 | blob | 解码 | 峰值 |
|---|---|---|---|---|
| audio/webm;codecs=opus | 可用 | 31407B | 48kHz 2ch 1.98s | 0.7373 |
| audio/webm | 可用 | 31407B | 48kHz 2ch 1.98s | 0.7479 |
| audio/ogg;codecs=opus | 内核不支持 | — | — | — |
| audio/mp4;codecs=mp4a.40.2 | 可用 | 33335B | 48kHz 2ch 1.96s | 0.7331 |
| audio/mp4 | 可用 | 32120B | 48kHz 2ch 1.90s | 0.7305 |

**关键结论：`decodeAudioData` 能解 MediaRecorder 输出的流式 webm/opus**（没有 duration 的 Live WebM），
峰值 0.73 说明采到的确实是真实音频而非静音。recAudio.js 的 AUDIO_MIMES 保持 webm/opus 首位即可，无需调整。
ogg 内核不支持但保留在候选里（跨浏览器兼容用，会自动跳过）。
没走「MediaRecorder 直接出 mp4/AAC 再抽出 AAC 帧」这条路：要自己解 mp4 容器找 moof/mdat +
处理 AudioSpecificConfig，复杂度远高于 opus→PCM→AAC 转码，而 192kbps AAC 转码音质无实际损失。

## 修复（下午 2）：v3.3 首录仍无声 —— AudioData 参数名写错 + 诊断解析器漏层

### 现象
14.27s / 24.3MB 产物。弹窗：音频链路=MediaRecorder采集→解码→AAC，PCM帧/AAC块=0/0，
「音频解码/编码失败: Failed to construct 'AudioData': Failed to read the 'numberOfFrames'
property from 'AudioDataInit': Required member is undefined」，且**产物含视频轨:否**。

### 定位
`scripts/mp4probe.py` 解产物：**trak[0] handler=avc1 count=349，视频轨完全正常**。
所以「产物含视频轨:否」是诊断代码自己的 bug，录制的视频部分一直没问题。

### 两个 bug
1. **AudioData 构造参数名写错（音频失败真凶）**：`AudioDataInit` 的成员是
   **`numberOfFrames`**，我写成了 `sampleFrames`（那是 AudioEncoder/VideoFrame 那侧的叫法）。
   抛 Required member is undefined → `encodeAudioToAac` 整个被 catch → 0 个 AAC 块 → 不建音轨。
   `src/recAudio.js:223` 已改。
2. **probeTracks 只扫 trak 的直接子 box（诊断误报）**：`hdlr` 在 `trak/mdia` 下、
   `stsz` 在 `trak/mdia/minf/stbl` 下，只遍历一层根本扫不到 → handler 恒为 null →
   video/soun 都报 0。已给 walkRange 加 `deep` 参数 + CONTAINERS 集合递归下钻。

### 回归（改完解析器必须拿真实产物跑一次）
新增 `scripts/probe-tracks-test.cjs`（node 跑，不依赖浏览器）验证 App.jsx 的解析逻辑：
```
07-41-07.mp4  vide/349样本              → 含音轨=false
05-34-31.mp4  vide/943 + soun/0样本     → 含音轨=false  ← 早上被误报成「有音轨」的，现在判对了
07-43-12.mp4  vide/201样本              → 含音轨=false
```

### 验证页增强
`测试工程/音频链路自检.html` 新增【4】PCM→AudioData→AudioEncoder(AAC) 环节
（1 秒 440Hz 合成音走一遍编码管线，报告 AAC 块数/字节）。
**为什么加**：上一版只测到 decodeAudioData+峰值，正好漏掉 AudioData 构造这一环，
所以全绿却仍然无声。现在采集→解码→编 AAC 全链路都覆盖到了。

## 收尾（下午 3）：v3.3 其实已成功，是自检把「有声」误报成「静音」

### 现象
33.92s / 66MB 产物。弹窗：PCM帧/AAC块=1543680/1508，产物含音轨=是(1508样本)，
但**音轨峰值:0.0031(静音!)**。用户打开视频实际**听得到声音**。

### 定位
`scripts/mp4probe.py` 解产物：trak[1] mp4a count=1508 32.17s，跟视频 32.28s 对齐 → **音轨真实有声**。
峰值 0.0031 是前导静音段的底噪。

### bug：probeAudioLevel 只采开头 800ms
旧实现把产物喂给 <audio> 实时回放，用 AnalyserNode 只在前 8×100ms 采样。
但录制前导有 ~2.7s 静音（先起 MediaRecorder → 全屏切换 → 注入播放脚本，首块 2749ms 即证据），
开头片段全是空白 → 全局峰值被空白段覆盖 → 把有声判成静音。

### 修复
`probeAudioLevel` 改用 `decodeAudioData` 解出整段 PCM、取**全局峰值**（秒级、自检不出声）：
- 避开前导静音段，峰值反映真实音量；
- 不再依赖实时回放，自检更快、且不会误采空白。
`src/App.jsx:531` 已改。`npm run build` 通过（39 modules）。

### 结论
v3.3 全链路（WebCodecs 视频 CBR + MediaRecorder 音频→解码→AAC，交错封装）**已可用**，
清晰度与声音兼得。录制弹窗里的「音轨峰值」现在能正确反映整段实际响度。
