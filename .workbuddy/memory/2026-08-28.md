  原计划的 ffmpeg 转码兜底（方案 C）因此作废，省下 80MB 依赖。
- 离屏录制：主进程开隐藏 BrowserWindow（show:false + backgroundThrottling:false）离屏跑时间轴，
  getDisplayMedia 捕获它 → 分辨率固定 1080P/2K/4K，与编辑器窗口大小彻底解耦，并省掉 canvas 逐帧裁剪。

  ③ 窗口移到屏幕外(x=-4000)实测帧宽被裁成 1868 不可用，`show:false` 反而能正常出帧。
- 端到端验证（测试工程真实页面）：放行前 paused/currentTime=0 → 放行后 currentTime=7.18 且翻到第 2 页，
  产物 MP4 1920×1080，画面像素随时间变化，说明真的录进去了。
- 顺带清理：`dist/` 因 `emptyOutDir:false` 堆积 26 个历史 js（5.6MB）且会被 electron-builder 全量打进 exe，
  已 `rm -rf dist && npm run build` 重建（302KB）。

## 【重要修正】录屏改为音画同源
- 第一版做成「画面取离屏页 + 声音取编辑器 iframe」，用户质疑会音画不同步。
  实测证实存在问题：两个独立播放实例 **22~52ms 恒定偏移**（不累积，但可感知）。质疑成立。
- 修正：`setDisplayMediaRequestHandler` 改为 `callback({video: frame, audio: frame})`，
  音视频都取自离屏窗口 → 偏移归零。实测捕获到 `Tab audio` 轨，产物同时含 mp4a/soun/vide。
- 静音策略随之**反转**：离屏页必须出声（muted 会让 audio 帧捕获不到），
  改由 App.jsx 在录制时静音编辑器内页面（新增 `setEditorAudioMuted`）。
- 顺带修音质：音频约束关掉 echoCancellation/noiseSuppression/autoGainControl，
  channelCount 从 1 → 2，避免口播人声被处理发闷。
- 性能实测（禁 GPU 软件渲染 + 双实例并行，保守下限）：离屏页 57fps、捕获流 27.2fps（目标 30）。
  v2 比 v1 更省 CPU（省掉 canvas 逐帧 drawImage），所以「离屏会更卡」的担心不成立。

## 修 bug：录屏启动失败 "Must pass filePath as a string"
- 根因：自己写的顺序 bug。`createRecWindow()` 内部第一行就调 `destroyRecWindow()`，
  而后者会清空 `recTmpFile` 并删掉临时文件。prepare 里却先写文件后建窗口 →
  文件被自己删掉、变量变 null → `loadFile(null)` 报错。
- 修复：交换顺序，先 `createRecWindow()` 再 `writeTempHtml()`。
- 顺带修隐藏缺陷：`recRoot` 只在「选择 HTML 文件」时记录，**刷新后从草稿恢复时为空**，
  会导致离屏录制静默退回窗口捕获兜底（webm、分辨率随窗口）。
  改为草稿存 `root` 字段，恢复时通过新增的 `zt:set-root` 回填。
- 教训：这类"清理函数会顺手清空共享变量"的顺序耦合，写代码时要在调用处写注释锁住顺序。

## 排查「离屏录制没声音」：逐个排除假设
- 已排除（都做了对照实测，均不是原因）：
  ① 捕获/播放先后顺序 —— 用应用同款顺序测，峰值 0.7372 有声；
  ② `preferCurrentTab: true` 劫持捕获目标 —— 带它照样抓到离屏窗口（画面米白、峰值 0.4476）；
  ③ 用户页面/audio 元素 —— 用其真实页面测峰值 0.8023。
- 自检升级：不只查「有没有音轨标记」，还用 `<audio>` + AnalyserNode 测**音轨电平峰值**，
  以区分「有音轨但静音」。只连 analyser 不连 destination，检测过程不出声。
- 自检结果改为**显示到顶栏**（「上次自检：音轨峰值 x.xxx」，静音标红），不再只靠 console.warn ——
  用户看的是终端，根本看不到 DevTools 里的日志，来回问了好几轮才发现这回事。
- 知识：终端里 `Autofill.enable / Autofill.setAddresses wasn't found` 是 DevTools 自身噪音，
  Electron 未实现 Chrome 的 Autofill 域，与录屏无关。
- 待验证：Chromium MediaRecorder 产出的是 **fragmented MP4**，Windows「电影和电视」等播放器
  常常只解视频不解音频。若自检峰值正常而播放器无声，需加重封装为标准 MP4
  （倾向纯 JS muxer，不引 80MB ffmpeg）。

## 静音定位：播放脚本压根没跑到 play()
- 用户实测定论：离屏模式、送入音轨 1、**产物含音轨：是、音轨峰值 0.0000（静音）** → 是真静音，不是播放器问题。
- 根因假设：用户页面带 4 个 `autoplay muted loop` 大视频（合计约 56MB），而生成的播放脚本用
  `window.addEventListener('load', setTimeout(startPlayback,300))` 启动。**load 事件要等所有子资源
  加载完**，被大视频拖住时 startPlayback 永远排不上队 → 音频与时间轴完全不启动；
  但 video 自带 autoplay 会照常循环，于是「画面在动却没声音」，极具迷惑性。
- 已加两层手段（待用户实测确认）：
  ① 探针：`zt:rec-state` IPC 抓离屏页真实状态（playCalls / released / playErr / audio.currentTime /
     fallback / activeSlide），录制开始 3 秒后 console.warn 出来；
  ② 兜底：REC_GATE 的 release() 里，若挂起队列为空（说明 play 从未被调用），
     主动调 `window.startPlayback()`（生成的播放脚本里它是全局函数，能连翻页 loop 一起起来），
     取不到再退回 `audio.play()`。仅在队列为空时触发，不影响正常流程。
- 教训：页面"看起来在动"不等于时间轴在走，autoplay 的 video 会伪装成正常运行。

## 全项目代码走读（熟悉架构）
- 架构核心：父窗口 React（App.jsx 2269 行，UI/状态/消息中转）↔ iframe（editorRuntime.js 2409 行，注入的纯脚本，直接操作真实 DOM），双向 postMessage。
- 关键链路：loadHtml → stripScripts 剥脚本 → rewriteAssets 资源转 blob（relMap 反查）→ 拼 STYLE_TAG+字幕数据+SCRIPT_TAG 注入 `</body>` → iframe srcdoc。
- 导出：exportClean 清编辑器足迹并重置首屏 active → 父端 restoreAndWrap 还原相对路径 + generatePlaybackScript 重生成播放脚本 → edited.html。
- 数据契约 `data-zt-*`：`data-zt-role="subtitle"` + start/end 相对秒数、`data-zt-id`、`data-zt-anim-effect/-duration/-delay/-return/-easing`、`data-zt-bound-to`（绑定写在字幕侧）、`focus-group`/`focus-item`。
- 注意坑：`selection` 消息不可清空 selectedSubIdx（否则解绑走错分支）；导出需重置 .slide active 否则首屏不显示；vite build 关了 emptyOutDir（避免批量删除触发安全确认）。
- 配套技能：`speech-visual-html/`（生成端 v5.4）、`vo-pipeline/`（edge-tts 口播产线 v1.0，实测通过）；`测试工程/speech-visual-test.html` 是 v5.3 契约回归夹具。
